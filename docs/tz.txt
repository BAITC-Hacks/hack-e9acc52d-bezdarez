Техническое задание
Проект «Аким на 5 часов» — AI-симулятор управления городом

Заказчик / владелец задачи: Astana Innovations
Тип продукта: интерактивный веб-симулятор
Формат разработки: хакатон, MVP за 5 часов
Рабочее название: QalaBalance
Версия ТЗ: 1.0
Основной язык интерфейса: русский
Дополнительный язык: казахский — вне обязательного MVP

1. Описание проекта

Необходимо разработать интерактивный веб-сервис, в котором пользователь получает фиксированный виртуальный бюджет города и принимает пять управленческих решений по следующим направлениям:

Транспорт.
Озеленение.
Социальная сфера.
Безопасность.
Городские сервисы.

В каждом направлении пользователь выбирает один городской проект и определяет объём его финансирования.

После распределения бюджета система должна рассчитать условный показатель качества жизни — Astana Quality of Life Score, показать изменение отдельных городских показателей и сформировать понятное AI-объяснение последствий принятых решений.

Сервис является демонстрационным симулятором. Все показатели, коэффициенты и результаты должны быть обозначены как модельные, а не как официальная оценка города Астаны.

2. Цель проекта

Создать понятный и визуально привлекательный симулятор, который демонстрирует:

ограниченность городского бюджета;
взаимосвязь различных сфер города;
положительные и отрицательные последствия решений;
эффект краткосрочного и долгосрочного планирования;
необходимость соблюдать баланс между направлениями;
возможность AI объяснять сложные результаты простым языком.
3. Целевая аудитория

Основные пользователи:

участники хакатона;
жители города;
молодые специалисты;
студенты;
сотрудники городских организаций;
участники образовательных мероприятий;
посетители презентаций Astana Innovations.
4. Ограничения MVP

В первой версии необходимо соблюдать следующие ограничения:

пользователь получает ровно 100 виртуальных бюджетных единиц;
пользователь должен принять ровно 5 решений;
одно решение принимается в каждой городской сфере;
в каждой сфере доступно минимум 3 проекта;
общий бюджет должен быть полностью распределён;
расчёт результата должен быть детерминированным;
одинаковые решения всегда должны давать одинаковый результат;
AI не должен самостоятельно рассчитывать итоговые баллы;
AI используется только для объяснения уже рассчитанного результата;
регистрация и авторизация не требуются;
база данных не требуется;
данные хранятся в статических JSON- или TypeScript-файлах;
результат может сохраняться в LocalStorage;
все показатели являются демонстрационными.
5. Основной пользовательский сценарий
Пользователь открывает стартовую страницу.
Знакомится с правилами симулятора.
Нажимает кнопку «Начать управление».
Видит исходное состояние виртуального города.
Последовательно выбирает один проект в каждой из пяти сфер.
Распределяет между сферами 100 бюджетных единиц.
Система проверяет корректность распределения.
Пользователь нажимает кнопку «Запустить симуляцию».
Система рассчитывает новые показатели.
Пользователь получает:
общий Astana Quality of Life Score;
сравнение показателей до и после;
краткосрочный и долгосрочный результат;
положительные последствия;
риски и компромиссы;
AI-объяснение;
реакции условных жителей;
профиль выбранной стратегии.
Пользователь может изменить решения и повторить симуляцию.
6. Пользовательские роли
6.1. Участник

Может:

запускать симуляцию;
выбирать проекты;
распределять бюджет;
просматривать результат;
менять горизонт планирования;
повторять симуляцию;
сохранять результат локально.
6.2. Администратор

Полноценная административная панель в MVP не требуется.

Настройка проектов, коэффициентов, исходных показателей и синергий выполняется через конфигурационные файлы проекта.

Административная панель может быть реализована после хакатона.

7. Структура приложения

Необходимо реализовать три основных экрана:

Стартовый экран.
Экран распределения бюджета.
Экран результата.
8. Функциональные требования
FR-01. Стартовый экран

Стартовый экран должен содержать:

название проекта;
краткое описание;
правила симуляции;
информацию о размере бюджета;
информацию о пяти направлениях;
предупреждение о демонстрационном характере данных;
кнопку «Начать управление».

Пример текста:

Вы получили 100 бюджетных единиц. Распределите их между пятью направлениями, выберите проекты и узнайте, как ваши решения повлияют на качество жизни виртуального города.

FR-02. Исходное состояние города

До начала распределения бюджета пользователь должен видеть стартовые показатели.

Показатель	Стартовое значение
Мобильность	54
Экология	50
Социальный комфорт	61
Безопасность	68
Городские сервисы	60
Общий AQLS	58

Все показатели оцениваются по шкале от 0 до 100.

На экране необходимо отобразить:

общий балл;
пять отдельных показателей;
радарную или столбчатую диаграмму;
краткие условные проблемы города.

Пример проблем:

загруженность дорог;
недостаток зелёных зон;
нагрузка на социальные учреждения;
недостаточное освещение отдельных территорий;
длительная обработка обращений жителей.
FR-03. Выбор проектов

Для каждого направления пользователь должен выбрать ровно один проект.

Каждая карточка проекта должна содержать:

название;
краткое описание;
рекомендуемый бюджет;
минимальный бюджет;
максимальный бюджет;
основные положительные эффекты;
возможные риски;
скорость получения результата;
расходы на дальнейшее обслуживание.

Пользователь не может выбрать два проекта в одной категории.

FR-04. Распределение бюджета

Общий бюджет составляет:

100 бюджетных единиц

Для каждого направления устанавливается бюджет от 5 до 40 единиц.

Интерфейс должен показывать:

общий бюджет;
уже распределённую сумму;
оставшуюся сумму;
превышение бюджета;
бюджет каждой сферы.

Пример:

Общий бюджет: 100
Распределено: 84
Осталось: 16

Кнопка запуска симуляции недоступна, если:

выбраны не все пять проектов;
распределено меньше 100 единиц;
распределено больше 100 единиц;
бюджет отдельного направления выходит за допустимые границы.
FR-05. Запуск симуляции

После нажатия кнопки «Запустить симуляцию» система должна:

Проверить входные данные.
Рассчитать влияние каждого проекта.
Применить синергии.
Применить отрицательные эффекты.
Рассчитать штраф за несбалансированный бюджет.
Рассчитать пять новых показателей.
Рассчитать итоговый AQLS.
Сформировать структурированные данные для AI.
Открыть экран результата.
FR-06. Результат «до и после»

Экран результата должен показывать:

Astana Quality of Life Score

58 → 71
     +13

Для каждого показателя должно отображаться изменение:

Показатель	До	После	Изменение
Мобильность	54	66	+12
Экология	50	58	+8
Социальный комфорт	61	67	+6
Безопасность	68	75	+7
Городские сервисы	60	76	+16

Конкретные значения должны зависеть от решений пользователя.

FR-07. Горизонт планирования

Пользователь должен иметь возможность переключать результат:

через 1 год;
через 3 года.

Переключение должно изменять:

общий AQLS;
показатели сфер;
текст объяснения;
список положительных эффектов;
риски;
реакции жителей.

Некоторые проекты должны давать быстрый результат, другие — долгосрочный.

Пример:

ремонт дорог эффективнее в первый год;
посадка деревьев сильнее влияет через три года;
строительство социальных объектов требует времени;
цифровые сервисы дают быстрый эффект;
расходы на обслуживание сильнее влияют в долгосрочном периоде.
FR-08. AI-объяснение

AI должен получать только рассчитанные системой данные.

AI не должен:

самостоятельно менять баллы;
придумывать статистику;
утверждать, что модель отражает официальные данные Астаны;
создавать факты, отсутствующие во входных данных;
ссылаться на несуществующие исследования.

AI должен возвращать:

краткое резюме результата;
три положительных последствия;
два или три риска;
объяснение основных компромиссов;
одну рекомендацию по изменению бюджета;
реакции условных жителей.
FR-09. Резервное объяснение

При недоступности AI приложение должно продолжать работать.

В этом случае объяснение формируется по шаблонам.

Пример:

Наибольший рост произошёл в сфере городских сервисов.
Основной вклад внёс проект «Цифровая платформа обращений».

Минимальный рост зафиксирован в социальной сфере.
Это связано с относительно небольшим объёмом финансирования.

Стратегия улучшила общий показатель качества жизни на 11 баллов.

Ошибка AI не должна блокировать экран результата.

FR-10. Реакции жителей

На экране результата необходимо показать четыре условные реакции:

пассажир общественного транспорта;
родитель школьника;
предприниматель;
житель жилого района.

Пример:

«Автобусы стали двигаться быстрее, но возле нашей школы изменений почти нет».

Реакции формируются на основании изменения соответствующих показателей.

FR-11. Профиль стратегии

После расчёта система должна определить профиль стратегии пользователя.

Возможные профили:

Технократ.
Зелёный управленец.
Социально ориентированный управленец.
Приоритет безопасности.
Сервисный реформатор.
Сбалансированный управленец.

Профиль определяется алгоритмом, а не языковой моделью.

Пример:

Ваш профиль: Технократ

Основная часть бюджета направлена на транспорт и цифровые сервисы.
Город стал эффективнее, однако социальная сфера получила меньше ресурсов.
FR-12. Повторная симуляция

На экране результата должны быть кнопки:

«Изменить решения»;
«Начать заново».

При выборе «Изменить решения» введённые значения сохраняются.

При выборе «Начать заново» настройки сбрасываются.

10. Алгоритм расчёта
10.1. Веса показателей
Мобильность:          25%
Экология:             20%
Социальный комфорт:   20%
Безопасность:         20%
Городские сервисы:    15%

Итоговая формула:

AQLS =
Мобильность × 0,25 +
Экология × 0,20 +
Социальный комфорт × 0,20 +
Безопасность × 0,20 +
Городские сервисы × 0,15
− штрафы
10.2. Зависимость эффекта от бюджета

Проект не должен расти линейно вместе с бюджетом.

Формула:

efficiency = Math.min(
  1.15,
  Math.sqrt(allocatedBudget / recommendedBudget)
);

Эффект проекта:

actualEffect = baseEffect * efficiency;

Пример:

рекомендуемый бюджет — 20;
выделенный бюджет — 10;
коэффициент эффективности — примерно 0,71;
проект реализует примерно 71% базового эффекта.

При бюджете выше рекомендуемого рост замедляется.

10.3. Горизонт трёх лет

Каждый проект должен иметь долгосрочный множитель.

Пример:

Проект	Множитель на 3 года
Адаптивные светофоры	1,2
Автобусные полосы	1,3
Ремонт дорог	0,9
Умный полив	1,4
Посадка деревьев	1,8
Расширение школ	1,5
Освещение улиц	1,2
Цифровая платформа	1,2

Формула:

threeYearEffect =
  baseEffect *
  efficiency *
  longTermMultiplier;
10.4. Штраф за несбалансированность

Если на направление выделено меньше 10 единиц:

Штраф: 0,25 балла за каждую недостающую единицу.

Если на направление выделено больше 30 единиц:

Штраф: 0,15 балла за каждую единицу выше 30.

Формула:

const lowPenalty = Math.max(0, 10 - budget) * 0.25;
const highPenalty = Math.max(0, budget - 30) * 0.15;

Общий штраф рассчитывается по всем пяти направлениям.

10.5. Расходы на обслуживание

Каждый проект имеет параметр maintenanceCost от 1 до 4.

Расходы на обслуживание сильнее влияют на результат через три года.

Пример формулы:

maintenancePenalty =
  horizon === "3y"
    ? Math.max(0, totalMaintenanceCost - 12) * 0.5
    : 0;
10.6. Ограничение значений

Каждый показатель должен находиться в диапазоне от 0 до 100.

const clamp = (value: number): number =>
  Math.max(0, Math.min(100, value));
11. Синергии проектов

Система должна учитывать сочетания проектов.

Первый проект	Второй проект	Дополнительный эффект
Адаптивные светофоры	Цифровая платформа обращений	+2 к городским сервисам
Автобусные полосы	Посадка деревьев	+2 к экологии
Благоустройство дворов	Освещение улиц	+2 к безопасности, +1 к социальной сфере
Мобильные медпункты	Центр реагирования	+2 к социальной сфере, +1 к безопасности
Умная уборка снега	Аналитика инцидентов	+1 к мобильности, +2 к сервисам
Умный полив	Оптимизация вывоза отходов	+2 к экологии, +1 к сервисам

Информация о найденных синергиях должна отображаться на экране результата.

13. AI-модуль
13.1. Назначение

AI используется только для интерпретации рассчитанного результата.

Схема:

Решения пользователя
        ↓
Детерминированный расчёт
        ↓
Готовые показатели и причины изменений
        ↓
AI-объяснение
        ↓
Текст для пользователя

19. Нефункциональные требования
19.1. Производительность
расчёт симуляции должен выполняться локально практически мгновенно;
интерфейс не должен зависать при изменении ползунков;
диаграммы должны обновляться без перезагрузки страницы;
AI-запрос не должен блокировать отображение основного результата.
19.2. Надёжность
приложение работает даже при недоступности AI;
ошибки API отображаются корректно;
некорректные данные не должны ломать интерфейс;
все числовые значения валидируются;
итоговые показатели ограничиваются диапазоном 0–100.
19.3. Безопасность
API-ключ не передаётся на клиент;
пользовательский ввод очищается;
на API устанавливается простое ограничение количества запросов;
приложение не собирает персональные данные;
регистрация не используется;
реальные данные жителей не обрабатываются.
19.4. Доступность
кнопки имеют понятные подписи;
элементы доступны с клавиатуры;
диаграммы сопровождаются текстовыми значениями;
ошибки не обозначаются только цветом;
основной текст имеет достаточный контраст.
20. Обработка ошибок
Недостаточно распределён бюджет
Распределите ещё 12 бюджетных единиц.
Превышен бюджет
Бюджет превышен на 7 единиц.
Уменьшите финансирование одного или нескольких направлений.
Не выбран проект
Выберите проект в категории «Социальная сфера».
Ошибка AI
AI-объяснение временно недоступно.
Показано объяснение, сформированное системой.
Ошибка конфигурации проекта
Не удалось загрузить данные проекта.
Проверьте конфигурационный файл.

23. Критерии приёмки

Проект считается готовым, если выполняются все следующие условия:

Пользователь может начать новую симуляцию.
Отображается исходное состояние города.
Доступно пять городских категорий.
В каждой категории доступно минимум три проекта.
Пользователь выбирает ровно один проект в каждой категории.
Пользователь распределяет ровно 100 бюджетных единиц.
Нельзя запустить симуляцию при неправильном бюджете.
Одинаковый набор решений всегда создаёт одинаковый результат.

Рассчитывается общий AQLS.
Отображается сравнение «до и после».
Работает переключение между одним и тремя годами.
Учитываются синергии и штрафы.
Отображаются риски и положительные эффекты.
При недоступности AI используется резервный текст.
API-ключ отсутствует в клиентском коде.
Приложение корректно работает при разрешении 1366×768.
На экране присутствует предупреждение о демонстрационном характере данных.
Пользователь может изменить решения и повторить расчёт.
В консоли браузера отсутствуют критические ошибки.
